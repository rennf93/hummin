Local models, step by step

Download a model, serve it, talk to it from your terminal. Everything here was battle-tested on a real homelab (UGREEN NAS with 128GB RAM + Apple Silicon Mac Mini with 32GB) over several weeks of daily use.

The one decision: which engine?

Two engines cover everything you will realistically want to run. Pick by model shape, not by preference:

llama.cpp (GGUF)colibri
Model typeDense models, or MoE models whose whole quant fits in your RAMFrontier MoE models far bigger than your RAM
Format.gguf filescolibri int4 group-64 safetensors containers (not GGUF!)
TrickEverything in RAM, optional GPUKeeps dense weights in RAM, streams experts from NVMe/SSD per token
SpeedFast (tens of tok/s on Apple Silicon)Slow but huge (0.5-3 tok/s for a 321B model)
Use it forDaily interactive codingOn-demand maximum quality, batch and privacy-sensitive runs

Rule of thumb: dense model that fits your RAM goes GGUF via llama.cpp. Frontier MoE bigger than your RAM goes colibri streamed from fast storage. If a GGUF exists for a colibri-only model, check llama.cpp architecture support first - new architectures often lag (GLM-5.3's glm5next is not merged into mainline llama.cpp yet).

32GB machines cannot hold GLM-5.3-Flash at all. That is not a tuning problem: the dense weight slice alone exceeds the RAM. Run it on the 64GB+ box and reach it over the network.

1Install hummin and point it at your servers

npm install -g hummin-cli

# ~/.zshrc - order is preference: first server serving a model wins,
# later duplicates become automatic fallbacks
export HUMMIN_COLIBRI_INSTANCES="http://nas:9996,http://nas:9998,http://mac:9998"
export COLI_API_KEY=your-key                   # omit if servers run keyless
VariablePurpose
HUMMIN_COLIBRI_INSTANCESComma-separated server base URLs; order = preference, duplicates dedupe into one picker entry with fallback ordering
COLI_API_KEYBearer token; a placeholder is sent for keyless servers
HUMMIN_COLIBRI_CTXFallback context window (default 16384), used only when a server does not report one

The extension autoloads from ~/.hummin/agent/extensions/. Sessions discover models at start, so restart the session after changing servers. Use IP addresses rather than .local names on mixed Linux networks - mDNS is flaky there.

2Download the model (on the right machine)

All downloads use the Hugging Face CLI and are resumable: if anything interrupts, just re-run the same command.

python3 -m pip install --user -U "huggingface_hub[cli]"
export PATH="$HOME/.local/bin:$PATH"

# GGUF, single file:
hf download unsloth/Qwen3.8-27B-GGUF --include "Qwen3.8-27B-UD-Q4_K_XL.gguf" \
  --local-dir /path/to/models/Qwen3.8-27B-GGUF

# A whole colibri container (~195GB, 62 shards) - same command shape:
hf download Justvugg/GLM-5.3-Flash-colibri-int4-g64 \
  --local-dir /path/to/models/GLM-5.3-Flash-colibri-int4-g64

If the download stalls at 0% with live processes, it is a Xet transfer hang. Kill the exact PIDs you started (never a name-pattern kill) and relaunch with HF_HUB_DISABLE_XET=1. Every long download we run uses this flag up front.

Download on the machine with the WAN pipe, not the machine that runs the model. A NAS moved ~14.4 MB/s aggregate with 8 parallel workers while a Mac single-stream managed only 1.3 MB/s. For hundreds of gigabytes, that is the difference between half a day and a month. Move files between machines over the LAN afterwards (2.5GbE shifts ~282 MB/s via ssh or rsync).

Long downloads pattern: nohup env HF_HUB_DISABLE_XET=1 hf download ... > download.log 2>&1 &, then watch with tail -f download.log and du -sh the target dir. Stop it by killing the exact PIDs from launch, never pkill -f hf.

3Serve it

Option A: llama.cpp on a Mac (launchd service)

brew install llama.cpp

llama-server --host 0.0.0.0 --port 9998 \
  --model /path/to/Qwen3.8-27B-UD-Q4_K_XL.gguf \
  --alias qwen3.8-27b --ctx-size 65536 --jinja --api-key YOURKEY

Expect ~17.6GB RSS plus ~64KB/token of KV cache - size --ctx-size to your RAM headroom. Run it under a launchd agent so it survives reboots and restarts on crash; a ready-to-edit plist template is on the reference page.

Option B: llama.cpp on Linux (docker compose)

services:
  qwen-27b:
    image: ghcr.io/ggml-org/llama.cpp:server
    restart: unless-stopped
    ports: ["9996:9996"]
    volumes: ["/volume1/ai-models/llama.cpp:/models:ro"]
    command: ["--host", "0.0.0.0", "--port", "9996",
              "--model", "/models/Qwen3.8-27B-UD-Q4_K_XL.gguf",
              "--alias", "qwen3.8-27b", "--ctx-size", "262144",
              "--threads", "4", "--jinja", "--api-key", "YOURKEY"]

Set --threads to your real core count - llama.cpp defaults to physical cores and undercounts efficiency-core CPUs. Context is cheap on big-RAM boxes: 262K is ~17GB of KV.

Option C: colibri for the frontier MoE models

# Grab the prebuilt runtime from github.com/JustVugg/colibri/releases,
# then (Linux example):
COLI_MODEL=/path/to/GLM-5.3-Flash-colibri-int4-g64 \
COLI_API_KEY=$(openssl rand -hex 24) \
  coli serve --ram 48 --host 0.0.0.0 --port 9998 --no-browser
  • --ram sizes the hot-expert cache; leave headroom for the OS and everything else on the box.
  • Verify a fresh download before trusting it: coli doctor --deep then coli plan. A broken republish once shipped with whole shard ranges empty, so a tensor census against config.json is worth the minute.
  • Keep it running and warm. The first generation after a start can take up to an hour (cold page cache); warm runs settle to seconds per token.
  • One generation at a time per instance - concurrent requests queue (HTTP 429). Run a second instance on another port and its own --ram budget if you need parallelism; expect 2-3x total throughput, not Nx, because instances share the disk pipe.

4Use it in hummin

hummin            # start a session
/model            # open the picker; your local models appear next to the zai catalog
/reload           # re-scan servers after you start or stop one
/thinking off     # disable reasoning for qwen-family models

What happens under the hood, so nothing surprises you:

  • Every model found on any configured server appears in one picker namespace, with a host badge. Unreachable servers contribute no models until a session restart - no guessed placeholder ids.
  • Context windows are read from each server's /props when available (llama.cpp serves it; colibri does not, so colibri models use HUMMIN_COLIBRI_CTX).
  • One generation at a time per server is handled for you: requests are serialized per server and 429 busy responses are retried with capped backoff.
  • Reasoning: qwen-family models map hummin's thinking level to chat_template_kwargs.enable_thinking, on by default; /thinking off disables it. Other families register without thinking controls.
  • Set httpIdleTimeoutMs to 0 (disabled) for local models - slow prefills otherwise look like dead connections.

Sanity check a new server before opening hummin: curl -s -H "Authorization: Bearer KEY" http://host:port/v1/models should list your model's id, and one small chat completion should stream. Everything hummin shows derives from these two calls.

5Keep it running

Servers you actually use daily should be launchd agents (Mac) or containers with restart: unless-stopped (Linux). The three rules we learned the hard way:

  1. Solo on small-RAM machines. Two GGUF servers on a 32GB Mac fight for page cache and both degrade. Check who is resident before starting another: ps aux | grep llama-server.
  2. CPU-only for giant MoE GGUFs on the Mac. --n-gpu-layers 0 is mandatory: Metal buffers for a 500GB-class model are a guaranteed OOM that takes down whatever else is running.
  3. Never glob /Volumes/* in launchd scripts on macOS. External-disk listings from launchd get TCC EPERM. Use exact paths, or mount network shares under your home directory (~/mnt/ai-models), which avoids the whole class of failure.

Troubleshooting

SymptomFix
Download stalls at 0%export HF_HUB_DISABLE_XET=1, re-run (resumes)
HTTP 401 in humminKey mismatch between server and client; test scripts must export the same key as the server
HTTP 429Server mid-generation; the extension retries automatically
Model missing from the pickerIts server was unreachable at session start; fix the server, restart the session (or /reload)
Picker shows the wrong context sizeServer was still loading during discovery; /props is only read at session start
First token takes forever on the NASCold colibri cache (up to 1h) or slow CPU prefill - use the fast machine for interactive work
llama.cpp slow on an efficiency-core CPUSet --threads to the real core count
unknown model architecture from llama.cppThe GGUF's architecture is newer than your llama.cpp build (GLM-5.3's glm5next is still unmerged upstream); use the colibri container instead
launchd server cannot find model files on an external diskTCC EPERM on /Volumes listings; use exact paths or a home-dir mount point
"Connection error" but the server is upClient missing the API key; keyless colibri servers accept any placeholder, enforced servers need the real one
