# Spec: Fix four tracked defects in Hummin

Scope: four open upstream `pi` issues that are present in the Hummin fork.
Hummin is a thin overlay on upstream `pi` (fork policy: zero deletions,
`@earendil-works/*` names preserved, no rename sweeps). These fixes touch
Hummin's own code under `packages/*`. They are not PRs to upstream; they are
local-to-fork corrections. Do **not** edit `packages/ai/src/models.generated.ts`
directly — regenerate from the generator script if that file is affected (it is not).

| Issue | Package | Severity | Size |
|-------|---------|----------|------|
| #9839 built-in tools ignore explicit custom `cwd` | coding-agent (tools) | regression (data-integrity) | small |
| #9792 persisted session file missing until first assistant msg | coding-agent (session-manager) | data-loss window | small |
| #9787 SDK import captures global undici dispatcher | coding-agent (http-dispatcher) | import-side-effect / embedded-host breakage | medium |
| #9807 TUI full re-render lag on 800+ message sessions | tui | performance | large |

## 1. #9839 — explicit custom `cwd` must win over `ctx.cwd`

**Status: confirmed in repo.** Regression introduced by
`62835ea81` (upstream PR #8627).

**Root cause.** #8627 changed every cwd-sensitive tool from
`resolveToCwd(path, cwd)` to `resolveToCwd(path, ctx?.cwd || cwd)` across
`bash.ts`, `edit.ts`, `find.ts`, `grep.ts`, `ls.ts`, `read.ts`, `write.ts`,
and `powershell.ts`. The intent was legitimate: when an extension registers
tools, `ExtensionContext.cwd` is the live session cwd after a `cd`. But it also
silently dropped the `cwd` that a consumer captured at tool-creation time
(e.g. per-workspace / per-project tool instances). `ctx.cwd` now always wins.

**Why the simple revert is wrong.** Reverting to plain `cwd` would lose the
#8627 fix that extensions rely on. The correct behavior is precedence, not a
global swap: an *explicitly created* custom cwd takes precedence over
`ctx.cwd`; otherwise `ctx.cwd` (the live session cwd) is used.

**Plan.**
1. Add an opt-in `customCwd` marker to `ToolsOptions` in
   `packages/coding-agent/src/core/tools/index.ts` (boolean: "the `cwd` passed
   to this factory is authoritative").
2. Thread it through the `createXTool` / `createXToolDefinition` factory pair
   so each tool closure records `this.customCwd = options?.customCwd === true`.
3. Change the resolution in all 8 tools from `ctx?.cwd || cwd` to
   `ctx?.cwd && !customCwd ? ctx.cwd : cwd` (i.e. use `ctx.cwd` only when the
   tool was **not** created with an explicit custom cwd).
4. Add a regression test in `packages/coding-agent/test/tools.test.ts`
   (mirrors the existing #8627 tests, but sets `customCwd` and asserts the
   custom cwd wins even when `ctx.cwd` differs).
5. Add a test asserting the *default* path still honors `ctx.cwd` (protects the
   #8627 behavior).

**Risk.** Low. Pure precedence logic; the resolution expression is the only
behavior change. Must not break existing `ctx.cwd` tests in `tools.test.ts`.

**Verification.** `npm run check`; run `packages/coding-agent` tool tests.

## 2. #9792 — persisted session must have a durable file at `create()` time

**Status: confirmed in repo.** `_persist()` (session-manager.ts ~1071) defers
disk write until an assistant message exists; `newSession()` sets
`sessionFile` but never writes the header. `isPersisted()` returns `true`
while no file exists.

**Root cause.** Contract in `newSession()`:
```
this.fileEntries = [header];
this.flushed = false;
if (this.persist) { this.sessionFile = join(dir, `${ts}_${id}.jsonl`); }
```
No file is written. The header only hits disk on the first assistant message
via `_persist()`'s `openSync(file, "wx")` flush. Between `create()` and that
first assistant turn, a normal process termination loses the session entirely,
even though `getSessionFile()`/`isPersisted()` promise durability.

**Plan.**
1. In `newSession()`, when `this.persist`, write the header to disk eagerly:
   ```
   if (this.persist) {
     const fileTimestamp = timestamp.replace(/[:.]/g, "-");
     this.sessionFile = join(this.getSessionDir(), `${fileTimestamp}_${this.sessionId}.jsonl`);
     writeFileSync(this.sessionFile, `${JSON.stringify(header)}\n`, { flag: "wx" });
   }
   ```
   Keep `this.flushed = false` so the existing flush/append logic is untouched
   (the header line is the only thing on disk; the assistant flush rewrites
   cleanly via `wx`, no duplicate header).
2. Do the same in the path-rename branch near session-manager.ts ~1572, which
   currently only writes when `hasAssistant`.

**Duplicate-header constraint (do not regress).** The comment at ~1572 notes
the deferred-write exists to avoid the `_persist()` no-assistant guard resetting
`flushed` to false and re-writing a second header. Writing **only the header
object** (the `[header]` array) at creation time is a single header line, so
it is safe. The assistant-flush `wx` rewrite then truncates and rewrites the
same single header — no duplication.

**Risk.** Low-medium. Must confirm no test asserts "file absent until first
assistant message" (that assertion is exactly what we're removing). Update such
tests to assert the file exists after `create()`.

**Verification.** Add a test: `create()` with `persist` must produce an existing
`.jsonl` containing a valid session header before any assistant message. Run the
`session-manager` test suite.

## 3. #9787 — SDK import must not capture the global undici dispatcher

**Status: confirmed in repo.** `packages/coding-agent/src/core/http-dispatcher.ts`
line 2: `import * as undici from "undici";` (static, module-scope). `undici` is
pinned to `8.10.2` (`packages/coding-agent/package.json`).

**Root cause.** undici `lib/global.js` installs a default `Agent` dispatcher
**at module load** when the registry is unset:
```
if (getGlobalDispatcher() === undefined) {
  setGlobalDispatcher(new Agent())
}
```
`http-dispatcher.ts` is on the SDK import graph:
`index.js → settings-manager.js → http-dispatcher.js`. So merely
`import`ing the SDK (no call to `configureHttpDispatcher()`) captures
`undici.globalDispatcher.1` with a foreign `Dispatcher1Wrapper(Agent)` from
pi's nested undici 8.10.2. Node's built-in `fetch` then dispatches through that
version-skewed default `Agent` for the process lifetime.

Two deterministic breakages in embedded hosts:
- Aborting a streamed mid-body fetch no longer tears down the server socket
  (server `close()` hangs).
- A completed streamed body can terminate early with `TypeError: terminated`.
Both stem from the cross-version `Dispatcher1Wrapper` shim mismatch. The capture
is load-order dependent (first writer wins), which is why it's flaky.

**Why the current guard doesn't help.** `configureHttpDispatcher()` already does
this deliberately:
```
undici.setGlobalDispatcher(dispatcher);
// Keep fetch and the dispatcher on the same undici implementation...
undici.install?.();
```
But it runs only on the CLI runtime entry points (`cli.js`, `rpc-entry.js`,
`main.js`, `interactive-mode.js`, `cli/setup.js`), never on the SDK import path.
The module-init install fires without that pairing.

**Plan.** Remove `undici` from the import-time graph of `http-dispatcher.ts`:
1. Delete the top-level `import * as undici from "undici";`.
2. Import `undici` lazily (static top-level `import type` for the types is OK;
   the runtime value is needed only inside the functions). Since this repo
   bans `await import()` inline (top-level imports only) and bans
   `enum`/dynamic type imports, use a **separate runtime module** for the
   undici call sites:
   - Create `packages/coding-agent/src/core/undici-runtime.ts` that owns the
     runtime `import * as undici from "undici";` and exports thin wrappers
     (`createOriginDispatcher`, `configureDispatcher`, `installGlobalFetch`)
     used by `http-dispatcher.ts`. Because `undici-runtime.ts` is only
     imported by the functions that actually configure the dispatcher, its
     module-init side effect cannot fire during the SDK import path.
   - Keep `import type { ... } from "undici"` (type-only, erased, no runtime
     side effect) in `http-dispatcher.ts` for the type annotations.
3. Alternatively (simpler, co-located): gate the runtime `import` behind the
   first call by moving `undici` usage into `configureHttpDispatcher`'s call
   chain in `undici-runtime.ts`. Prefer this approach — one small module,
   no structural spread across the file.

**Design note.** The cleanest robust option is the dedicated
`undici-runtime.ts` module: it's the single place that imports the runtime
`undici`, so any future import graph can be audited in one file, and the
module-init install is confined to the deliberate configuration entry point.

**Risk.** Medium. `http-dispatcher.ts` is imported transitively by the SDK
entry; must confirm the lazy module is never pulled onto the static import
graph of `index.js`/`settings-manager.js`. The existing test
`packages/coding-agent/test/http-dispatcher.test.ts` must still pass and should
gain an assertion that importing the SDK does not change
`globalThis[Symbol.for("undici.globalDispatcher.1")]`.

**Verification.** `npm run check`; run `http-dispatcher.test.ts`; add the
"SDK import does not capture dispatcher" assertion.

## 4. #9807 — incremental (cell-level) rendering for large sessions

**Status: SKIPPED (2026-09-22, user decision).** Measured before implementing:
with 800 realistic messages (Markdown assistant turns, tool-call components)
inside a ScrollView, a full frame renders in 0.2–0.3 ms (static, scroll, and
post-invalidation). The memoization Phase A proposes already exists:
- `Markdown`/`Text` cache rendered lines per width (markdown.ts, text.ts)
- `BashExecutionComponent` caches wrapped output lines
- the layout pipeline keeps a per-frame `renderCache` (layout.ts) so each
  component renders at most once per frame
- nothing invalidates the tree per frame (`Tui.invalidate()` fires only on
  cell-size responses and theme/capability changes)

If real-world lag on a large session reproduces, profile it first (--cpu-prof
or the render-churn-bench) — the hotspot is likely elsewhere (streaming
component churn, an extension component, search highlighting), not the
scroll-view render path. Do not re-attempt Phase A/B on the basis of this
spec's unmeasured premise.

**Original (unverified) root cause claim.** The TUI re-derives and renders every message line on each
interaction (typing, scrolling). With 800+ messages (~1.7MB JSONL) this becomes
visibly laggy. OpenTUI avoids this with cell-level diffing: it only re-renders
the cells that changed and reuses the rest of the previous frame.
(Disproven by measurement, see Status above.)

**Plan (phased — this is the large one).**
- **Phase A (safe, high value):** isolate the hot path.
  - Memoize each message's rendered lines keyed by (entry id, content hash,
    theme key) so re-renders reuse cached line buffers instead of re-formatting.
  - Only re-render the viewport region + a margin rather than the full stack;
    skip rendering off-screen lines beyond a large threshold.
  - Guard re-render with a dirty check comparing new vs. previous scroll state
    (the `changed` checks already exist at scroll-view.ts ~180/~194 — extend to
    a per-region dirty set).
- **Phase B (the real fix):** cell-level diffing.
  - Track per-message line ranges in the previous frame; on re-render, compute
    the diff and only overwrite changed cells. This is the OpenTUI approach.
  - Requires a stable identity per message (already have `id`) and a way to map
    cell coordinates back to messages.

**Sizing.** Phase A is a bounded, low-risk optimization achievable without a
render-architecture rewrite. Phase B is a larger change to the render pipeline
and is gated behind a decision after Phase A is measured.

**Risk.** Medium (Phase A) / higher (Phase B). Any change to `scroll-view.ts`
rendering must preserve existing scroll/follow-end behavior and pass
`packages/tui/test/` (there is a `tui-render.test.ts` and `render-churn-bench.ts`).

**Verification.** `npm run check`; run the tui render tests; use `bench/` to
confirm no regression. Prefer Phase A now; defer Phase B unless the user wants
the full diffing rewrite.
